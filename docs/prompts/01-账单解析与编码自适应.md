# Prompt 链 01 · 账单解析：从「能读」到「读对」

> 说明：本文件是开发过程的 Prompt 快照，按真实顺序整理。提问保留原始意图与约束，
> AI 的回答只摘录与代码落点相关的部分；每个偏差都对应仓库里真实存在过的失败与修复。

## 0. 背景

赛题要求「校园 / 垂直社区全栈 MVP」。选题定为「个人消费账单赛博算命」后，
第一个硬问题不是算命，而是**账单读不进来**：支付宝、微信、银行导出的 CSV 列名不同、
编码不同、前置说明行不同，还有「交易关闭」这类非消费行。解析层一旦读错，
后面所有卦象都是假的。因此这条链的目标是：**让解析层对格式差异免疫，并且错误可解释。**

## 1. 第一轮 Prompt（原文）

```
我要做一个「账单起卦」的 Web 应用，先把解析层做扎实，不急着做 UI。

输入：用户从支付宝或微信导出的 CSV 文件（ArrayBuffer）。
要求：
1. 不要假设列顺序，也不要假设表头就在第一行——导出文件通常有 5-10 行说明文字。
2. 编码可能是 UTF-8、带 BOM 的 UTF-8、GBK。不要用「猜」，要用能抛错的解码器试。
3. 金额可能是 "¥88.80"、"-88.80"、"88.80元"、带千分位的 "1,234.56"，不要用浮点累加。
4. 时间可能是 "2026-10-03 12:34:56"、"2026/10/3 08:05"、"2026年10月3日"。
5. 单行坏了不要整份失败：跳过并计数，最后告诉我跳了几行。
6. 输出一个 ParsedBill：清洗后的流水 + 总行数 + 跳过行数 + 告警 + 识别到的格式与编码。

先给我 types.ts 和 parse 目录下的三四个文件，别写 React。领域层必须是纯函数，
我要能直接用 vitest 跑，不依赖浏览器。
```

### AI 首版产出

- `src/domain/parse/values.ts`：`parseAmountToCents`、`parseTimestamp`
- `src/domain/parse/decode.ts`：`decodeBillBuffer`（UTF-8 BOM → UTF-16LE → UTF-8 → GB18030）
- `src/domain/parse/csv.ts`：前 12 行找表头、列名语义映射、坏行跳过
- `src/domain/types.ts`：`Txn` / `ParsedBill` / `CategoryKey`

首版能跑通支付宝样例，但下面这些偏差在真实样例上全部暴露了。

## 2. 我发现的偏差（按发现顺序）

| # | 现象 | 根因 | 影响 |
| --- | --- | --- | --- |
| 1 | 「10月房租」「电影票」「密室逃脱」全被归为「其他」，必需占比被算成 35%，初爻误判为阴 | 列名 hints 里 `/商品说明/` 和 `/交易对方/` 映射到了同一个 `merchant` 字段，商品说明被吞 | 卦象直接错（该阳的爻变阴） |
| 2 | 微信账单里工资 ¥9,000 被算成支出，结余率 -5073.8% | `direction` 的 hints 包含 `/^交易类型$/`，而微信这一列的值是「商户消费 / 转账」，被当成了收支方向 | 收入/支出全反 |
| 3 | 「昆明地铁-地铁月卡」「乐刻健身-健身年卡」被判成订阅 | 订阅关键词里写了「月卡 / 年卡」 | 四爻虚高，订阅月供虚高 |
| 4 | 「电饭煲」「面馆」被归为餐饮 | 餐饮关键词用了过于宽泛的「饭」「面」 | 分类结构失真，处方开错方向 |
| 5 | 「朋友生日礼物」被归为购物 | `shopping` 规则排在 `social` 之前 | 人情支出被算成情绪消费 |
| 6 | 空白账单落成「坤为地」 | 六爻在 0 数据时全部判阴，仍然成卦 | 假卦（最严重的一类错误） |

## 3. 第二轮引导 Prompt（原文）

这一轮的关键不是「再写一遍」，而是**只改被指出的三处，其余不动**，并给出可验证的输入。

```
解析层大体对了，但有 4 个具体错误。请只改这几处，不要重写整个文件：

1. 列名映射：/商品说明/ 和 /交易对方/ 不能都映射到 merchant。新增 detail 列键，
   商品说明/商品/摘要/备注 归 detail。分类时要同时看 merchant + detail。
2. 方向列：/^交易类型$/ 不能算 direction 的 hint。微信这一列是「商户消费/转账」。
   direction 只认：收/支、收支、收支金额、借贷标志、方向。
3. 订阅关键词删掉「月卡」「年卡」，只认会员/VIP/续费/订阅/具体平台名。
4. 餐饮关键词里删掉「饭」「面」这种单字，换成具体词：学校食堂、盖饭、炒饭、米线、
   麻辣烫、沙县、快餐、卤味、烧烤。
5. 人情（social）规则排到购物（shopping）之前，并加上「礼物 / 生日礼」。

改完请顺手做两件事：
- 把「同一商户多种写法」的归一化单独抽成一个函数，例如
  「支付宝-美团外卖（北京）有限公司」和「财付通-美团外卖****旗舰店」归一后必须相等；
- 空账单（0 笔支出）要显式返回「无卦」，不能落成坤卦。

验收标准：samples 里四份账单跑出来的分类与卦象要和我给的表一致（我会贴输出）。
```

### AI 修正后的落点

- `parse/csv.ts`：`COLUMN_HINTS` 增加 `detail`；`classify(direction, merchant, detail, rawType)` 同时吃三个字段
- `categories.ts`：规则优先级重排 `subscription → housing → transport → medical → learning → food → daily → entertainment → social → shopping → transfer → income`；关键词具体化
- `parse/normalize.ts`：`normalizeMerchant` 去「支付宝-」「财付通-」「有限公司」「网络科技」「****」、括号门店名、≥6 位订单号
- `hexagram.ts`：`expenseTxnCount === 0` 时返回 `id: 0 / name: "无卦" / symbol: "—"`，人格 `no-ledger`，处方空数组

## 6. 复盘：这条链教会模型什么

1. **「不要猜」要落成解码器选择**：`new TextDecoder("gb18030", { fatal: true })` 抛错即判断，比猜编码可靠一个量级。
2. **列名映射要区分「展示字段」与「语义字段」**：商户是对方，商品说明是买了什么，混在一起分类必错。
3. **关键词表是产品逻辑，不是技术细节**：`饭`/`面` 这种单字会把「电饭煲」「面馆」卷进来，必须具体化。
4. **空数据要有显式的「无」**：宁可显示「无卦」，也不能让算法编出一个像模像样的假卦 —— 这条原则后来贯穿了整个项目。
