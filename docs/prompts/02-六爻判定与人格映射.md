# Prompt 链 02 · 六爻判定：把「玄学」压成一张可核对的阈值表

> 这是整个项目的核心创意落地环节。难点不在写六十四卦表，
> 而在**让卦象、人格、处方共用同一套判定，不许各自解释**。

## 0. 背景

「账单算命」最容易滑向两个坑：

- **纯随机**：每次刷新卦象都变，评审一眼看穿是装饰；
- **各算各的**：卦象用一套规则、人格用另一套规则，用户会发现「卦说我能存钱，人格说我月光」。

因此这条链的目标是：**六爻 → 卦象 → 人格 → 处方，共用同一个判定入口，结果可复算。**

## 1. 第一轮 Prompt（原文）

```
现在做「起卦」这一层。要求：卦必须是从账单算出来的，不能有随机数。

六个爻位，每个对应一个真实指标，阈值你来提建议，但必须能一句话解释：
1. 初爻：生存必需（房租/吃饭/通勤/日用/药品）占支出比例
2. 二爻：情绪消费（购物+娱乐）占支出比例
3. 三爻：深夜（23:00-05:00）支出笔数占比
4. 四爻：自动续费类商户个数
5. 五爻：结余率
6. 上爻：预算烧穿日（第几天）

输出：
- evaluateLines(ctx) 是唯一判定入口，卦象和人格都必须调它，不许各写一套；
- 三爻组一个八卦，按「自下而上」编码；上下卦查表得 64 卦（文王卦序），
  卦符用 Unicode 4DC0 起的那一段；
- 卦辞要按阴阳格局自动生成，带真实数字；
- 另外给我一个 dominantLeakIndex：多个阴爻时，哪一爻「最疼」按可回收金额排，
  不要按爻位顺序取第一个。

先不要写 React。给我 types + hexagram.ts + persona.ts。
```

### AI 首版产出

- `evaluateLines` 统一判定；`trigramOf(bottom, middle, top)`；`HEXAGRAMS[upper][lower]` 64 卦表
- 卦辞按阴阳串与漏点生成
- `persona.ts`：按最疼阴爻映射 6 种人格 + 0 阴（铁算盘）+ ≥4 阴（散财童子）

首版把「算法骨架」搭对了，但有三处口径问题。

## 2. 我发现的偏差

| # | 现象 | 根因 | 影响 |
| --- | --- | --- | --- |
| 1 | 编译直接报 `TS1136 Property assignment expected` | 64 卦表数组少了一个 `},` | 整个模块不可用 |
| 2 | 月光账单也被判「已超支 = false」 | `alreadyOver` 只看「外推是否超预算」，而不是「实际累计是否已超」 | 结论与账单事实相反 |
| 3 | 人格与卦象偶尔对不上（同一份账单，卦说两处漏，人格说订阅问题） | 人格函数自己又算了一遍指标，阈值与 `evaluateLines` 漂移 | 自相矛盾，答辩必被追问 |
| 4 | 空账落成坤卦 | 0 数据时所有阈值判定为阴 | 假卦 |

## 3. 第二轮引导 Prompt（原文）

```
方向对了，但规则要收紧，请按下面改，别改别的：

1. 只允许一个判定入口：evaluateLines(ctx)。persona / prescription 需要指标时，
   从 evaluateLines 的结果或 ledger 取，禁止自己再写一遍阈值。哪一爻「最疼」也用
   可回收金额算，不要用「第一个阴爻」。
2. alreadyOver 的定义改成：实际累计支出是否已经超过预算（不是预测）。
   月光样例应该返回 true，它是真的超支了。
3. 空账（支出 0 笔）返回「无卦」：id 0、name 无卦、symbol —、人格 no-ledger、处方空。
4. 卦辞要能解释「为什么是这个卦」：把六爻阴阳串、上下卦、以及每个漏点的名字写进去。
5. 阈值表单独导出一个 THRESHOLDS 常量，并写进注释：为什么必需占比是 60%、
   情绪消费是 20%、夜行是 12%、订阅是 2 个、结余是 15%、燃尽是第 26 天。

验收：
- 四份样例的卦象/人格/燃尽日/处方金额必须与我给的表一致；
- 同一份账单连续算两次，JSON 要逐字节相同（不许有 Date.now / Math.random）。
```

### AI 修正后的落点

- `hexagram.ts`：`THRESHOLDS` 常量 + `LINE_META` 元数据（position / metric / leak / punch）
- `dominantLeakIndex`：只在阴爻中比较「可回收金额」，权重分别是
  必需品缺口、情绪消费超出部分、夜间支出、订阅月供、结余缺口、燃尽快慢
- `runway.ts`：`alreadyOver = actualBurnDay !== null`，燃尽日先取实际、后取外推
- `persona.ts`：改为消费 `evaluateLines` 的结果（`BY_LINE` 6 种 + `IRON` + `SCATTER`）
- `prescription.ts`：按 `monthlySavingCents` 降序取前三，每条带 3 步动作与账单证据

## 4. 最终阈值表（写进代码注释，也是答辩时的解释依据）

| 爻位 | 指标 | 阳（守住） | 阴（有漏） | 为什么是这个阈值 |
| --- | --- | --- | --- | --- |
| 初爻 | 必需支出占比 | ≥ 60% | < 60% | 低于 60% 意味着四成以上的钱花在可选项上，底盘不稳 |
| 二爻 | 购物 + 娱乐占比 | ≤ 20% | > 20% | 经验上 20% 是「有娱乐但没失控」的分界 |
| 三爻 | 夜间支出笔数占比 | ≤ 12% | > 12% | 深夜支付的边际快乐最低、后悔率最高 |
| 四爻 | 订阅商户数 | ≤ 2 个 | ≥ 3 个 | 3 个以上通常已经记不清自己在付什么 |
| 五爻 | 结余率 | ≥ 15% | < 15% | 15% 是能覆盖一次意外的下限 |
| 上爻 | 燃尽日 | ≥ 26 天或无断点 | ≤ 25 天 | 月末最后一周是「撑住」与「断崖」的分水岭 |

## 7. 复盘：这条链教会模型什么

1. **一个事实只能有一个计算入口**：`evaluateLines` 是唯一入口，人格与处方只消费结果，不重算。
2. **预测与事实必须分开**：`alreadyOver`（已发生）与 `burnoutDay`（外推）是两件事，混在一起就会得出「超支了但没超支」。
3. **阈值要写进常量并解释**：`THRESHOLDS` 让评审可以直接质疑某个数字，而不是对着一堆魔法数发呆。
4. **玄学外观 + 可核对规则**：卦符、爻辞是包装；真正说服人的是「点开每一爻能看到指标、阈值、判词」。
