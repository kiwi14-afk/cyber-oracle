## 1 项目概述

### 1.1 问题选择：为什么是「账单算命」

大学生记账类应用的普遍失败原因不是「不能记」，而是**记完没有反馈**。用户看到的是一张分类饼图和一句「本月支出 ¥1,367.90」，这既不能告诉他「哪儿出了问题」，也不能告诉他「什么时候会撑不住」。记账的终点应该是一个判断，而不是一个数字。

本项目把「判断」做成两层：

- **一层是结构**：六项真实财务指标 → 六爻 → 卦象 → 人格；
- **一层是时间**：中位日耗 → 外推 → 燃尽日 → 三剂处方。

而「算命」只是这层结构的外壳。外壳的价值在于**让用户愿意看第二次**：卦名、爻辞、人格标签是可分享的社交货币，燃尽日与处方是可执行的行动。二者缺一不可——只有玄学是玩具，只有数字是报表。

### 1.2 关键设计取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 起卦是否随机 | **完全不随机** | 随机卦象无法被评审复现，也无法让用户信任；六爻改为六个可解释指标 |
| 账单是否上云 | **不上云** | 原始商户与金额是最敏感的数据；解析与起卦全在浏览器内完成 |
| 模型是否算账 | **不算** | 账由确定性引擎算完，模型只做措辞，从根上消除数字幻觉 |
| 无 Key 是否可用 | **完整可用** | 答辩现场、评审环境不应依赖任何私有凭据 |
| 卦符是否用 Unicode | **自绘** | 部分系统字体缺 U+4DC0 段，会回落成方块；自绘还顺带满足断网可用 |

### 1.3 与评分维度的对应

| 维度（权重） | 本项目的落点 |
| --- | --- |
| 过程可复现性与演进链路 25% | 22 次细粒度提交 + 3 条完整 Prompt 链 + 10 分钟复现路径 |
| 解题有效性与实用价值 25% | 燃尽日、三剂处方、四份样例的固定输出基线 |
| 方法创新性与意图控制 20% | 数据信封 + 五条铁律 + 四段结构 + 双通道降级（本文第 2 章） |
| 工程质量与架构设计 15% | 单向依赖分层、金额整数分、纯函数、26 单测、strict 类型 |
| 用户体验与产品精细度 15% | 六爻逐爻点亮、点爻看证据、预算实时重算、无 Key 不白屏 |

## 2 意图控制策略

这一章是本项目的技术主张：**AI 的能力应该被限制在它真正擅长的部分。**
账单应用里，模型擅长措辞，不擅长算术与事实核验。因此架构上把「算」与「说」彻底切开。

### 2.1 三类失败模式与对应设计

| 失败模式 | 表现 | 对应设计 |
| --- | --- | --- |
| 算错 | 把 ¥1,367.90 说成「不到 1,400」，或自行计算「环比增长 12%」 | 信封只给**已格式化字符串**，提示词禁止换算 |
| 编造 | 出现「你还有 3 笔星巴克订阅」「下月房租要涨」 | 铁律「卦案里没有的一律不写」；信封不含上月数据 |
| 跑偏 | 输出 600 字理财课，或开始评价人格缺陷 | 四段结构 + 260–420 字上限 + 禁用清单 |

### 2.2 数据信封（Payload）

信封是模型能看到的**全部世界**。它由 `toPayload()` 生成，约 1 KB：

```json
{
  "v": 1,
  "month": "2026-10",
  "income": "¥2,300.00",
  "expense": "¥1,367.90",
  "net": "+¥932.10",
  "savingRate": "40.5%",
  "essentialShare": "73%",
  "emotional": { "amount": "¥333.00", "share": "24.3%" },
  "night": { "count": 3, "amount": "¥106.00", "share": "8%" },
  "subscriptions": { "count": 3, "amount": "¥36.00", "items": ["网易云音乐", "视频会员", "云盘"], "share": "2.6%" },
  "categories": [{ "label": "居住", "amount": "¥510.00", "share": "37.3%", "count": 2 }],
  "hexagram": {
    "id": 37, "name": "风火家人", "symbol": "第37卦", "leakCount": 2,
    "judgement": "六爻自下而上为「阳阴阳阴阳阳」，上巽下离……",
    "lines": [{ "position": "初爻 · 食宿根基", "yin": false, "value": "73%", "text": "初爻得位……" }]
  },
  "persona": { "name": "情绪结算员", "tagline": "你不是在买东西，你是在给情绪结账。", "description": "……" },
  "runway": { "budget": "¥2,300.00", "dailyBurn": "¥20.90", "burnout": "不会见底", "daysInMonth": 31, "elapsedDays": 26, "budgetSource": "income" },
  "prescriptions": [{ "title": "给非必需品加 72 小时冷静期", "saving": "¥72.00", "oneLiner": "……", "steps": ["……"], "evidence": "购物 ¥288.00，2 笔，占支出 21%" }],
  "top": [{ "label": "房东王姐 · 10月房租", "amount": "¥450.00", "date": "2026-10-01", "category": "housing" }]
}
```

三个刻意的设计：

1. **数字预格式化**。「引用一个字符串」比「计算一个数」的错误率低一个量级；模型没有机会做四舍五入。
2. **不给比较素材**。信封里没有上月、没有同龄人均值、没有收入预测，模型想编「环比」也无从下手。
3. **把判断也写进去**。`judgement`、`persona`、`runway` 都已由本地引擎得出，模型只做「复述 + 解释」，不做「判定」。

> 设计原则：**信封里有什么，模型才能说什么；信封里没有的，就是它不该说的。**

### 2.3 系统提示：五条铁律与四段结构

`ORACLE_SYSTEM_PROMPT` 全文见附录 A。核心是两段：

```
【铁律】
1. 账已经由确定性引擎算完。你只解释，不计算、不换算、不新增任何数字。
2. 只能引用卦案里出现的金额、百分比、日期、商户名；卦案里没有的，一律不写。
3. 不提供投资、借贷、贷款、法律、医疗建议；不预测收入变化。
4. 不评判人格缺陷，只点评账单结构；可以犀利，不可以羞辱。
5. 用中文，口语，短句，克制，有画面感。不要 Markdown 标题、不要列表符号、不要表情。

【输出结构】共 260-420 字，分四段，段间空一行：
第 1 段：一句断语，不超过 20 字，点出人格与「能不能撑到月底」。
第 2 段：讲最疼的一爻是哪一爻、为什么疼，引用该爻的真实数值。
第 3 段：讲燃尽日与日均速率的关系，指出结构性问题。
第 4 段：只给一个今天就能执行的动作，并说明它每月能省多少钱。
```

四段结构不只是排版需要，它同时承担三件事：

- **可校验**：第 2 段必须带该爻数值，评审可以逐字比对信封；
- **防跑偏**：420 字上限内塞不进理财课；
- **可降级**：本地卦辞用同一套四段结构，因此「AI 挂掉」时版式不跳变，只是措辞从模型换成本地。

### 2.4 双通道与降级矩阵

```
浏览器 ──(POST 聚合信封)──► /api/oracle ──(SSE)──► 上游模型
   ▲                            │
   └──── mode: "local" ◄────────┘  （无 Key / 上游失败 / 超时）
```

| 场景 | 服务端行为 | 前端表现 |
| --- | --- | --- |
| 未配置 `AI_API_KEY` / `AI_MODEL` | 立即返回 `{ mode: "local" }` | 展示本地四段卦辞，角落标注「本地卦辞 · 未经任何模型」 |
| 上游 401 / 429 / 500 | 捕获后仍返回 200 + `mode:"local"` + `reason` | 展示本地卦辞，标注「上游异常，已降级」 |
| 上游 45 秒未响应 | 主动中断，同上 | 同上，不出现无限转圈 |
| SSE 流中途断开 | 前端保留已收到的文本 | 已生成部分照常显示，不整段丢弃 |
| 上游返回非 SSE（JSON 一次性） | 前端按 `content-type` 分流 | 一次性渲染，不报错 |

关键实现：路由永远返回 HTTP 200。**降级不是错误，是另一条正常路径。**
前端据此决定「用哪一份文本」，而不是「弹一个红框告诉用户配置 Key」。

### 2.5 让约束可验证

意图控制如果只写在提示词里，就无法证明。项目用三件事让它可验证：

1. **本地卦辞作为对照组**：`localNarrative(payload)` 与模型共用同一份信封、同一套四段结构。评审可以把两段并排看，判断模型有没有「多算」。
2. **数字溯源**：信封里每个数字都是格式化后的唯一写法（`¥1,367.90` / `40.5%` / `第 23 天`），把输出里任意数字拿去搜索，命中即为合规、未命中即为幻觉。
3. **拒绝路径可演示**：把 `AI_BASE_URL` 改成不可达地址，页面仍然完整——这比任何「我们做了容错」的说明都有说服力。

### 2.6 追问通道的额外约束

追问（`CHAT_SYSTEM_PROMPT`）只加三条，但都很硬：

- 只依据卦案回答，看不到的直接说「这份账单里看不到」；
- 140 字以内，直接回答，不铺垫、不重复卦辞；
- 问「怎么办」时，必须给「一个动作 + 一个数字」，不给一串原则。

历史只带最近 4 轮，问题上限 300 字 —— 这两条是成本控制，也是防止上下文被拖偏。

## 3 架构设计

### 3.1 分层与依赖方向

```
            ┌───────────────────────────────┐
            │  app/  页面 + /api/oracle,/chat│  渲染与传输
            └───────────────┬───────────────┘
                            │
            ┌───────────────▼───────────────┐
            │ components/  六爻/燃尽/处方/卦辞│  纯展示
            └───────────────┬───────────────┘
                            │
            ┌───────────────▼───────────────┐
            │ lib/ai/  信封/提示词/流式解析  │  AI 薄层
            └───────────────┬───────────────┘
                            │
            ┌───────────────▼───────────────┐
            │ domain/  解析→聚合→燃尽→卦象   │  纯函数，无 IO
            │          →人格→处方→编排      │  无 React / 无浏览器依赖
            └───────────────────────────────┘
```

依赖单向，不允许回指。这条约束的收益是可被验证的：

- 领域层可被 vitest 直接跑（26 例，1.5 秒）；
- 领域层可被 `vite-node` 直接跑成 CLI（`npm run inspect`）；
- 领域层可在浏览器里直接跑（`parseBillBuffer` / `buildOracle`）。

**同一套代码、三个入口、结果逐字一致** —— 这是「过程可复现」在代码层面的证据。

### 3.2 数据模型

```ts
Txn            // 单笔流水：date/ts/amountCents/direction/category/merchant/merchantKey/hour/isSubscription
ParsedBill     // 解析结果：txns/totalRows/skippedRows/warnings/encoding/format/month
Ledger         // 聚合结果：收支/分类/按日/按时/订阅/夜间/必需/结余率/中位数
Runway         // 燃尽：预算及来源/日均/安全日额/累计点/燃尽日/是否已超
Hexagram       // 卦象：id/name/symbol/上下卦/判词/advice/六爻/漏点数
Persona        // 人格：key/name/tagline/description/traits/dominantLine
Prescription   // 处方：id/title/oneLiner/steps/saving/difficulty/evidence
OracleResult   // 编排结果：以上全部 + verdict
```

三条硬约定：

1. **金额只用「分」整数**（`amountCents`），浮点只在展示层出现；全部聚合用整数加减。
2. **时间解析一次到位**：解析时算出 `ts`（epoch）与 `date/hour`，聚合层不再碰 `Date`。
3. **领域层无副作用**：没有 `Date.now()`、没有 `Math.random()`、没有 IO —— 这是「同一份账永远同一卦」的前提，也是单测能断言「两次计算结果逐字节相等」的原因。

### 3.3 解析管线

```
ArrayBuffer
  ├─ ① 解码 decode.ts        UTF-8 BOM → UTF-16LE → 严格 UTF-8 → GB18030 → 宽松 UTF-8
  ├─ ② 表头探测 csv.ts       前 12 行找「同时含时间与金额」的行，命中列数最多者胜
  ├─ ③ 列语义映射           时间/金额/方向/商户/商品说明/交易类型 六类 hint
  ├─ ④ 值解析 values.ts      ¥、千分位、括号负数、中文日期、Excel 序列号
  ├─ ⑤ 商户归一 normalize.ts 去渠道前缀/公司后缀/门店括号/订单号
  ├─ ⑥ 分类 categories.ts    规则优先级：订阅→居住→交通→医疗→学习→餐饮→日用→娱乐→人情→购物→转账→收入
  └─ ⑦ 月份过滤              只保留流水最多的那个月，并在 warnings 里说明
```

①的「不猜编码」是刻意的：`new TextDecoder("gb18030", { fatal: true })` 对非法字节抛错，
「抛错即判断」比任何启发式猜测都可靠。`samples/bill-wechat-gbk.csv` 就是这条路径的回归用例。

### 3.4 账本聚合的三条口径

| 口径 | 规则 | 为什么 |
| --- | --- | --- |
| 资金搬运不计消费 | 转账 / 还信用卡 / 余额宝进出归 `transfer`，直接跳过 | 否则信用卡账单会被「还款 + 消费」重复计两遍 |
| 退款计为收入 | 不做「负支出」 | 保证支出总额单调、可解释 |
| 只分析一个月份 | 流水最多的月份 | 混月会让燃尽日与结余率同时失真 |

派生指标：`essentialShare`（必需占比）、`nightShare`（夜间金额占比）、
`subscription.count`（按商户去重）、`savingRate`（结余率）、`medianExpenseCents`（单笔中位数）。

### 3.5 燃尽算法

```ts
elapsedDays   = 最后一笔流水所在日（至少 1）
dailyBurn    = median(有过消费的那些天的支出)     // 中位数而非均值，抗「一笔房租」干扰
budget       = 手填额度 > 0 ? 手填 : (有收入 ? 收入 : 本月支出)
actualBurnDay= 累计支出第一次 > 预算的那一天
burnoutDay   = actualBurnDay ?? 外推中第一个超预算的日子
alreadyOver  = actualBurnDay !== null
```

三个细节决定结论是否可信：

- **用中位数**：房租一笔 ¥450 会把均值抬到失真，中位数不会；
- **已过天数取「最后一笔流水日」**：如果账单只导到 20 号，不能按 31 天摊；
- **实际优先于外推**：已经烧穿的日子是事实，不是预测；两者混用会得出「超支了但没超支」的荒谬结论。

页面上还给了「日均可用余额」（`budget/days`），让用户能直接对比「我今天花了多少 vs 我今天能花多少」。

### 3.6 六爻判定

唯一判定入口是 `evaluateLines(ctx)`，卦象、人格、处方全部复用它。阈值集中为 `THRESHOLDS` 常量：

| 爻位 | 指标 | 阳（守住） | 阴（有漏） | 解释 |
| --- | --- | --- | --- | --- |
| 初爻 食宿根基 | 必需支出占全部支出 | ≥ 60% | < 60% | 低于 60% 意味着四成以上花在可选项上，底盘不稳 |
| 二爻 情绪口子 | 购物 + 娱乐占比 | ≤ 20% | > 20% | 20% 是「有娱乐但没失控」的经验分界 |
| 三爻 夜行 | 23:00–05:00 笔数占比 | ≤ 12% | > 12% | 深夜决策质量最低、后悔率最高 |
| 四爻 订阅寄生 | 订阅商户数 | ≤ 2 个 | ≥ 3 个 | 3 个以上通常已记不清在付什么 |
| 五爻 储蓄锚 | 结余率 | ≥ 15% | < 15% | 15% 是能覆盖一次意外的下限 |
| 上爻 燃尽 | 预算烧穿日 | ≥ 第 26 天 或 无断点 | ≤ 第 25 天 | 最后一周是「撑住」与「断崖」的分水岭 |

**卦象编码**：下三爻（初/二/三）组下卦，上三爻（四/五/上）组上卦，
按「自下而上」的二进制映射到八卦（乾 111 / 兑 110 / 离 101 / 震 100 / 巽 011 / 坎 010 / 艮 001 / 坤 000），
再查文王卦序表得 64 卦与 Unicode 卦符（U+4DC0 + id − 1）。

**主导漏点**：不是「取第一个阴爻」，而是在阴爻中比较**可回收金额**：

| 爻 | 可回收金额的算法 |
| --- | --- |
| 初爻 | 支出 × max(0, 60% − 必需占比) |
| 二爻 | 购物 + 娱乐金额 |
| 三爻 | 夜间金额 |
| 四爻 | 订阅月供 |
| 五爻 | max(0, 收入 × 15% − 净结余) |
| 上爻 | max(0, 外推总额 − 预算) |

这条让「哪一爻最疼」有金额依据：学生样例里二爻（¥333）比四爻（¥36）疼，因此二爻主导。评审可以自己算一遍。

### 3.7 人格映射

人格不是随机标签，而是「最疼的那一爻 → 一种人」，外加两条真实数据当证据：

| 条件 | 人格 | 一句话 |
| --- | --- | --- |
| 无支出流水 | 无账可看 | 没有支出流水，就没有人格可读 |
| 六爻全阳 | 铁算盘 | 六爻皆稳，钱在你手里有秩序 |
| 阴爻 ≥ 4 | 赛博散财童子 | 不是某一处漏，是到处都在漏 |
| 主导 = 初爻 | 浮基生存家 | 先买快乐，再想办法活到月底 |
| 主导 = 二爻 | 情绪结算员 | 你不是在买东西，你是在给情绪结账 |
| 主导 = 三爻 | 深夜破防者 | 白天很清醒，23 点后换了个人 |
| 主导 = 四爻 | 订阅寄生体 | 每月被十几笔小额自动扣款养着 |
| 主导 = 五爻 | 月光巡航员 | 工资到账即离场，账户只是中转站 |
| 主导 = 上爻 | 月中断崖客 | 月中就见底，后半月靠意志与借款撑 |

1–3 处漏时，`tagline` 会追加次要漏点，例如「（同时：订阅还在自动续）」——
这句不是装饰，是把六爻结构压缩成一句可复述的自述。

### 3.8 处方引擎

一条处方必须同时满足：**有金额、有动作、有证据**。

```
候选生成（按规则触发）
  ├─ 订阅清理     count > 0 且 (count ≥ 2 或 月供 ≥ ¥50)   省 70% / 30%
  ├─ 夜间纪律     夜间占比 ≥ 10% 或 夜间金额 ≥ ¥50         省 60%
  ├─ 餐饮降级     餐饮占比 ≥ 25% 或 日均 ≥ ¥25             省 12%
  ├─ 娱乐封顶     娱乐占比 ≥ 8%                            省 30%
  ├─ 购物冷静期   购物占比 ≥ 12%                           省 25%
  ├─ 人情月度池   人情占比 ≥ 6%                            省 20%
  ├─ 先存后花     结余率 < 15% 且有收入                    补足到 15%
  └─ 兜底两条     现金信封挑战 / 闲置回血                  按日均推算
排序：按 monthlySavingCents 降序 → 去重 → 取前 3
```

每条处方带 `difficulty`（今天就能做 / 需要一点规则 / 需要换习惯）与 `evidence`（引用本账单的具体数字）。
落地时特别注意「可执行」：不是「你要省钱」，而是「把购物车移到收藏夹，三天后再决定」。

### 3.9 前端编排

`OracleApp` 是唯一 client 编排器，`page.tsx` 保持 server component，只挂主流程与噪点层。

```
landing  ──选择/拖拽/样例──►  parsing  ──①解码 ②解析 ③聚合 ④起卦 ⑤处方──►  board
   ▲                                                                         │
   └─────────────────────────────「换一份账单」──────────────────────────────┘
```

- **进度是真实的**：五个步骤各自 `await sleep()` 推进，而不是一段假动画；
- **起卦在浏览器内**：`parseBillBuffer` 与 `buildOracle` 是纯函数，`TextDecoder("gb18030")` 浏览器原生支持；
- **`/api/*` 只收聚合信封**：`toPayload()` 的结果约 1 KB，原始流水一行不出设备；
- **卦辞先本地成文再流式替换**：`localNarrative` 立即渲染，AI 文本到了逐字替换，视觉上不闪不空。

组件拆分：`atoms.tsx`（Panel/SectionHead/Chip/Metric/Dot）、`BillDropzone`、`HexagramPanel`、
`HexGlyph`（自绘卦符）、`RunwayPanel`（echarts 按需引入 + ResizeObserver）、
`CategoryPanel`（横条比较而非饼图）、`PersonaCard` + `PrescriptionCards`、`NarrativePanel`、`ChatPanel`。

## 4 工程质量

### 4.1 类型与构建

- `tsconfig` 开启 `strict`、`noUncheckedIndexedAccess` 等，`any` 不出现在领域层；
- 构建产物：`/` 静态预渲染，35.9 kB 页面代码 / 139 kB First Load JS，共享块 103 kB；
- 两个 API 路由均声明 `runtime = "nodejs"`，避免把流式响应送进 Edge 运行时。

### 4.2 测试策略（26 例）

| 文件 | 例数 | 覆盖 |
| --- | --- | --- |
| `tests/parse.test.ts` | 15 | 金额边界（0 / 空 / 括号负数 / 千分位）、时间边界（2 月 30 日、Excel 序列号）、GBK 与 BOM、表头探测、方向列、坏行跳过、多月过滤、商户归一 |
| `tests/engine.test.ts` | 11 | 四份样例的卦象 id/名/人格/燃尽日/处方条数、结余率、预算手填改变燃尽日、空账返回无卦、两次计算逐字节一致 |

领域层单测的价值不在覆盖率数字，而在**把产品口径钉死**：任何一次阈值或排序改动，都会让某条断言变红。

### 4.3 四份样例的固定输出（回归基线）

| 样例 | 结构 | 收支 | 卦象 | 人格 | 燃尽 | 处方 |
| --- | --- | --- | --- | --- | --- | --- |
| `bill-student.csv` | 43 笔 UTF-8 | 收 ¥2,300.00 / 支 ¥1,367.90 / 40.5% |  37 风火家人（上巽下离） | 情绪结算员 | 不会见底 | ¥181.79/月 |
| `bill-moonlight.csv` | 52 笔 | 收 ¥6,200.00 / 支 ¥6,647.00 / −7.2% |  2 坤为地（六爻全阴） | 赛博散财童子 | 第 23 天 | ¥1,740.95/月 |
| `bill-steady.csv` | 26 笔 | 收 ¥9,500.00 / 支 ¥6,403.00 / 32.6% |  1 乾为天（六爻纯阳） | 铁算盘 | 不会见底 | ¥458.06/月 |
| `bill-wechat-gbk.csv` | 26 笔 GB18030 | 收 ¥9,199.00 / 支 ¥1,126.90 / 87.7% |  25 天雷无妄（上乾下震） | 情绪结算员 | 不会见底 | ¥207.41/月 |

前三个覆盖「能过但不稳」「全线失守」「六爻皆稳」三种极端；第四个专门验证编码与列名不是对着支付宝写死的。

### 4.4 双入口一致性

`npm run inspect -- samples/xxx.csv` 在终端输出的卦象、六爻、卦辞、燃尽、处方，
与网页完全一致 —— 因为它们调的是同一个 `buildOracle`。
这条比任何「架构图」都更直接地证明了「UI 不是另写一套逻辑」。

### 4.5 性能

- echart 按需引入（core + line + grid + tooltip + markLine），不引入完整包；
- `RunwayPanel` 用 `ResizeObserver` 在容器变化时 `resize()`，避免重复建实例；
- 首屏不做 AI 请求，只有进入卦盘后才发一次 ~1 KB 的信封请求；
- 解析 43 笔账单在浏览器内耗时 < 30 ms（`performance.now()` 实测）。

## 5 可复现性论证

「过程可复现」是本次评分权重最高的一项。本节给出的不是承诺，而是**可以被评审复做的路径**。

### 5.1 无 Key 降级矩阵

| 配置状态 | 卦象/人格/燃尽/处方 | 卦辞 | 追问 |
| --- | --- | --- | --- |
| 无 `AI_API_KEY` | 完整 | 本地四段，完整 | 返回说明文案，不报错 |
| 有 Key，上游正常 | 完整 | 模型流式四段 | 模型回答，140 字内 |
| 有 Key，上游 401/500/超时 | 完整 | 本地四段 + 原因标注 | 说明文案 |

结论：**没有任何一条功能以「必须有 Key」为前提**。这也让演示视频可以在两分钟内切换两种模式。

### 5.2 断网与离线依赖

| 依赖 | 处理 |
| --- | --- |
| 在线字体 | 不使用；全部走系统字体栈 |
| 卦符字形 | 自绘（铜金阳爻 / 朱砂阴爻），不依赖 U+4DC0 段是否有字形 |
| CDN 资源 | 无；`npm ci` 之后即可断网运行 |
| 样例账单 | 随仓库分发；`predev` / `prebuild` 同步到 `public/samples/` |

> 同一个限制也解释了本文档的排版：Windows 自带的雅黑、宋体、等线均**不含 U+4DC0 段**，
> 直接写卦符在 PDF 与 README 里会变成空白或方块，因此正文统一用「第 N 卦 卦名」表达，
> 卦符只在界面里以自绘形式出现。这不是回避，而是同一份字体现实的两面。

### 5.3 样例同步机制

`samples/` 是唯一真相，`public/samples/` 是构建产物且已 `.gitignore`。
`scripts/sync-samples.mjs` 在 `predev`、`prebuild` 自动执行（实测 4 个样例 13.5 KB），
前端「一键体验」直接 `fetch('/samples/bill-student.csv')` —— 于是「网页样例」与「测试样例」不可能漂移。

## 6 用户价值与产品细节

### 6.1 三重反馈

| 层 | 用户看到 | 解决的心理问题 |
| --- | --- | --- |
| 卦象 | 卦名 + 卦符 + 一句断语 | 「我这个月到底怎么样」——一句话结论 |
| 六爻体检 | 六条指标，点开看阈值与判词 | 「凭什么这么说」——可核对 |
| 燃尽 + 处方 | 第几天见底 + 三条可执行动作 | 「那我该怎么办」——可行动 |

三者顺序是刻意的：先给结论，再给依据，最后给动作。反过来（先给一堆数字）就是记账 App 的老路。

### 6.2 交互细节

- **六爻逐爻点亮**：自下而上 60 ms 递增，模拟「画卦」；`prefers-reduced-motion` 下降级为直接显示；
- **点爻看证据**：每一爻可展开（指标 / 阈值 / 判词），把「玄学」摊开成「体检报告」；
- **预算实时重算**：手填额度后，燃尽日立即重算（月光样例：第 23 天 → ¥3,000 预算下第 6 天），
  页面标注「这是『可复算』的现场证明」；
- **结论可复制**：一键复制「卦名 + 人格 + 结余率 + 燃尽 + 处方省额」，方便分享；
- **隐私提示前置**：上传区直接写「解析与起卦全部在浏览器本地完成 · 文件不会上传到任何服务器」。

### 6.3 视觉系统

| 令牌 | 值 | 用途 |
| --- | --- | --- |
| 墨 | `#07080B / #0C0E13 / #12151C / #191D26 / #232834` | 背景与面板层级 |
| 朱砂 | `#E2453C / #C63128` | 阴爻、亏损、警示 |
| 铜金 | `#E4B457 / #C9922F` | 阳爻、主强调、数字高亮 |
| 薄荷青 | `#38D9A9 / #1FA98A` | 正向结余、守住 |
| 纸 | `#F3EEE3 / #CFC6B6 / #9C9486 / #6E685E` | 正文层级 |

视觉上刻意避免三件事：不用渐变铺底（只用细描边 + 噪点层）、不用圆角卡片堆叠、不用彩色 icon。
卦符用铜金与朱砂两色自绘，让「阳/阴」在缩略图尺寸下也能分辨。

## 7 局限与后续

| 局限 | 现状 | 后续 |
| --- | --- | --- |
| 只支持 CSV | 支付宝/微信/银行 CSV 已覆盖，PDF/截图不支持 | 增加 OCR 导入（端侧或服务端） |
| 分类靠关键词 | 覆盖常见商户，长尾会落到「其他」 | 引入商户别名表 + 用户一次性纠正记忆 |
| 单月分析 | 只分析流水最多的月份 | 多月对比：卦象变化曲线、订阅净增 |
| 模型质量依赖上游 | 语气与洞察随模型波动 | 增加本地小模型通道；输出打分器自动重试 |
| 无账号体系 | 无登录、无云端同步 | 若做多端，需先解决「账本加密存储」再谈同步 |

最后一条是刻意的克制：账单是最敏感的个人数据，在没有把握之前，不做云端同步是更负责的选择。

### A 提示词全文（`src/lib/ai/prompts.ts`）

```
你是「赛博卦账」的卦师，负责把一份已经算好的账单卦案讲给当事人听。

【铁律】
1. 账已经由确定性引擎算完。你只解释，不计算、不换算、不新增任何数字。
2. 只能引用卦案里出现的金额、百分比、日期、商户名；卦案里没有的，一律不写。

4. 不评判人格缺陷，只点评账单结构；可以犀利，不可以羞辱。
5. 用中文，口语，短句，克制，有画面感。不要 Markdown 标题、不要列表符号、不要表情。

【输出结构】共 260-420 字，分四段，段间空一行：
第 1 段：一句断语，不超过 20 字，点出人格与「能不能撑到月底」。

第 3 段：讲燃尽日与日均速率的关系，指出结构性问题（不是「你要省钱」这种废话）。
第 4 段：只给一个今天就能执行的动作，并说明它每月能省多少钱。

【语气示例】
「你不是不会赚，是不会留。钱在发薪日当天就被安排完了。」
```
