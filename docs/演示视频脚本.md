# 演示视频脚本 · 赛博卦账

> 目标：**7 分钟**内讲完「问题 → 产品 → 结构 → 意图控制 → 工程可信度」，
> 其中 **AI 协同过程复现占 2 分 10 秒**（赛题硬性要求 ≥2 分钟）。
> 全文口播稿可直接照读，按时间码推进即可。

## 0 录制准备（录之前 10 分钟做完）

| 项 | 设置 |
| --- | --- |
| 窗口 | 浏览器窗口 1440×900（或 1280×800），缩放 100%，隐藏书签栏 |
| 终端 | 字号 16–18pt，深色主题，清屏后只留必要输出 |
| 页面 | 先打开 `http://localhost:3000`，确认 4 个样例卡片可见 |
| 数据 | 只用仓库内虚构样例，**绝不录真实账单** |
| 声音 | 普通话，语速偏慢；不配 BGM（评审听口播更清楚） |
| 字幕 | 建议后期加关键数字字幕（¥1,367.90 / 第 23 天 / 26 passed） |
| 录屏 | 1080p 30fps，鼠标移动放慢，点击前停顿 0.5 秒 |

启动命令（录制前跑一遍确保服务在）：

```bash
npm run dev          # 终端 1：3000 端口
# 终端 2 备用（可选）：npm run inspect -- samples/bill-student.csv
```

## 2 分段脚本

### 2.1 0:00–0:25 开场

**画面**：落地页顶部（标题「把一个月账单算成一卦」）。

**口播**：

> 这是一个把账单算成卦的应用，叫赛博卦账。
> 它解决的不是记账，是「记完账之后你仍然不知道自己下个月会不会饿肚子」。
> 我用七天做了这个全栈应用，代码、提示词、测试、文档全部在仓库里。

### 2.2 0:25–1:05 痛点与方案

**画面**：鼠标从标题移到六个爻位说明段落，再移到「卦不是随机落出来的，是算出来的」。

**口播**：

> 大多数记账 App 给你一张饼图，然后告诉你本月支出多少。
> 但真正让人焦虑的是两件事：我这个月到底怎么样，以及我还能撑几天。
> 所以我做了六个真实的财务指标：必需占比、情绪消费、夜行、订阅、结余、燃尽。
> 每个指标越界，就是一爻阴；越界越多，卦就越差。
> 关键在于——同一份账单，永远得到同一卦。这是可以被你复算的。

### 2.3 1:05–2:25 主流程走查

**画面**：点「学生 · 生活费型」样例 → 解析进度 → 卦盘。鼠标依次停在卦名、三项指标、六爻面板。

**口播**：

> 这是 43 笔流水的学生账单，浏览器本地解析，三秒出结果。
> 第 37 卦，风火家人，上巽下离。为什么是这一卦？因为六爻自下而上是阳、阴、阳、阴、阳、阳。
> 这里有一个细节：卦符是我自己画的。Unicode 的六十四卦符号在多数系统字体里没有字形，
> 会显示成方块——所以阳爻画成铜金整条，阴爻画成朱砂两段，断网也不会坏。
> 三项核心数字：支出 ¥1,367.90，结余率 40.5%，订阅每月 ¥36.00。
> 再往下，六爻体检：每一爻都有指标、阈值和一句判词，点开就能看到「凭什么这么说」。
> 二爻是这一卦最疼的地方：购物和娱乐占了 24.3%，¥333.00，其中购物是最大的口子。

### 2.4 2:25–3:05 可复算的现场证明

**画面**：点「换一份账单」→ 月光样例 → 卦盘（坤为地、第 23 天见底）→ 在「本月可用金额」里输入 3000。

**口播**：

> 换一个月光账单：收入 ¥6,200，支出 ¥6,647，结余率负 7.2%。
> 六爻全阴，第 2 卦坤为地，第 23 天见底——也就是说，这个月的最后八天是借来的。
> 现在我在预算框里把额度改成 ¥3,000，注意看这里。
> 燃尽日从第 23 天变成第 6 天，预算来源从「按收入」变成「手填额度」。
> 这就是「可复算」的现场证明：卦不变，但结论随着你的预算假设实时重算。

### 2.5 3:05–3:35 输入鲁棒性

**画面**：回到落地页，拖入 `samples/bill-wechat-gbk.csv`（或点上传选择该文件）→ 卦盘顶部显示文件名与识别结果。

**口播**：

> 这份是微信导出的账单，GB18030 编码，列名和支付宝完全不同。
> 解码顺序是：UTF-8 BOM、UTF-16、严格 UTF-8、GB18030——
> 用能抛错的解码器试，而不是猜。26 笔流水正常入账，没有乱码。
> 解析层遇到坏行只跳过并计数，不会让整份账单失败。

### 2.6 3:35–4:05 隐私与 CLI

**画面**：上传区下方的隐私声明 → 切到终端，运行 `npm run inspect -- samples/bill-student.csv`。

**口播**：

> 这里写着「解析与起卦全部在浏览器本地完成，文件不会上传到任何服务器」。
> 这不是文案：解析和起卦调用的是领域层的纯函数，原始流水一行都不出设备；
> 送给模型的只有一个约 1 KB 的聚合信封。
> 同一套领域层，在终端里也能跑。命令是 npm run inspect。
> 终端算出来的是第 37 卦、风火家人、40.5%——和网页一模一样。
> 三个入口、一套逻辑，这是我说「可复现」的底气。

### 2.7 4:05–6:15 AI 协同过程复现（核心段，2 分 10 秒）

这一段要证明的不是「我用了 AI」，而是**我如何控制 AI，以及如何验收它**。

**画面 1（4:05–4:35）**：终端 `git log --oneline`，缓慢滚动。

**口播**：

> 先说演进链路。仓库里是 22 次提交，不是一次 initial commit 一把梭。
> 顺序是：骨架、领域模型、解析、聚合、燃尽、卦象、人格、处方、测试、CLI、AI 层、API、UI、修复。
> 你能看到我先做可测试的正确性，再做界面——因为卦要是算错了，界面再好看也没意义。

**画面 2（4:35–5:20）**：打开 `docs/prompts/01-账单解析与编码自适应.md`，滚到「我发现的偏差」表格。

**口播**：

> 这是三条 Prompt 链里的第一条：账单解析。
> 第一轮我给 AI 的约束很具体：不要假设列顺序、不要猜编码、金额不要用浮点、坏行跳过要计数。
> 它一次就给出了能跑的版本，但在真实样例上暴露了六个问题。
> 最要命的是这个：`商品说明` 和 `交易对方` 被映射到同一个字段，导致「10 月房租」被归到「其他」，
> 必需占比从 73% 掉到 35%，初爻该阳的变阴——卦象直接错。
> 我的第二轮 Prompt 不是「重写」，而是只改这几处，并给了验收标准。
> 这就是意图控制的第一层：**约束要能落到可验证的断言上**。

**画面 3（5:20–6:00）**：打开 `docs/prompts/03-AI卦辞的意图控制.md`，停在「信封」与「铁律」两节。

**口播**：

> 第三条链是 AI 卦辞，也是这次比赛最想讲的部分。
> 账单应用一旦让模型读原始流水，就会出现三类事故：算错、编造、跑偏。
> 我的做法是把「算」和「说」彻底切开：账由本地引擎算完，模型只负责讲。
> 信封里所有数字都是**已经格式化好的字符串**，比如 ¥1,367.90、24.3%、第 23 天；
> 系统提示里写死五条铁律：不计算、不新增数字、不给投资建议、不羞辱人格、不用 Markdown。
> 输出固定四段，260 到 420 字。第 2 段必须引用那一爻的真实数值——
> 这样评审可以把输出里的每个数字拿去信封里搜，搜不到就是幻觉。

**画面 4（6:00–6:15）**：终端运行 `npm test`，26 绿。

**口播**：

> 而这一切是可以被测试约束住的。26 个单测里有一条最硬：
> 同一份账单连续算两次，JSON 必须逐字节相同。
> 也就是说，随机数、Date.now、浮点误差，任何一个混进来，测试就会红。

> **（若现场有 API Key，可选加 30 秒）** 填入 Key 后重启，卦辞面板会从「本地卦辞」切成「AI 卦辞」，
> 逐字流式出现；把 Base URL 改成不可达地址，它又会退回本地——不白屏、不报错。

**画面 5（可选，若时间富余）**：编辑器里把 `THRESHOLDS.emotionalShare` 从 0.2 改成 0.25 → `npm test` 变红 → 改回 → 变绿。

### 2.8 6:15–6:50 工程质量

**画面**：终端依次 `npm run typecheck`、`npm test`、`npm run build`，停在 build 输出。

**口播**：

> 三条硬指标：TypeScript strict 零错误、26 个单测全绿、生产构建通过。
> 首页 First Load JS 139 kB，图表按需引入，没有 UI 组件库，没有在线字体。
> 装完依赖可以断网运行，评委在自己的机器上十分钟能复现。

### 2.9 6:50–7:10 收尾

**画面**：回到卦盘全景，缓慢上滚一次，最后停在仓库地址 / README 首屏。

**口播**：

> 最后一句：这个应用不预测你的未来，它只是把你已经做过的事，用一张卦摊开。
> 卦不吓人，爻位说话——先补最下面那道口子，上面的自然不容易塌。
> 代码、Prompt 链、技术文档都在仓库里，欢迎复算。

## 3 录制操作清单（照着点，不会乱）

1. 打开 `http://localhost:3000`，等 2 秒让动画结束再开始录。
2. 点样例卡片时用鼠标慢慢移到卡片中央，点击后停 1 秒再移开。
3. 卦盘出现后先停在卦名 2 秒，再依次指 3 项指标、六爻。
4. 「换一份账单」在页面右上角；切换后等卦盘重新出现再说话。
5. 预算输入框：先全选（Ctrl+A）再输入 3000，避免出现「23003000」。
6. 上传 GBK 样例用拖拽更直观；拖入前把文件管理器窗口先摆好。
7. 终端命令逐条执行，每条执行完停 1 秒再念下一条。
8. `git log` 用 `--oneline` 并限制条数：`git log --oneline -12`。
9. 打开 Markdown 文档时把字号调到 130%，只滚到需要的那张表。
10. 结尾停在 README 的「10 分钟复现」一节，方便评委按图索骥。

## 4 需要避免的坑

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 录到真实账单 | 隐私事故，直接失分 | 只用 `samples/` 里的虚构样例 |
| 把 Key 出现在画面里 | 凭据泄露 | 录前清空 `.env.local`，或录制时不要打开该文件 |
| 端口没起来就开录 | 空鏡头重录 | 先跑一遍完整流程再正式录 |
| 语速太快念数字 | 评审听不清关键结论 | 数字前后各停 0.3 秒 |
| 长时间无操作 | 观感拖沓 | 每段不超过 40 秒静止画面 |
| 只讲功能不讲意图控制 | 丢掉 20% 权重 | 4:05–6:15 这段必须完整保留 |
